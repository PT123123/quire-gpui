## 1. 允许为 GPUI 改动 `quire-core` 到什么程度

- 现状：`AGENTS.md` 写的是"复用 quire-core，默认锁定旧版 rev"，即**不改 core**。
- 冲突点：core 里没有中文文案（`core/*/label()` 是英文，中文词表在桌面 `state.rs:14992` 附近）；core 没有跨进程 ID 分配（MCP stdio 桥因此存在，`mcp.rs:17`）；设备 ID 持久化、Job 泵、MergeCtx 的 10 个分配闭包都在壳侧。
- 选项：A 完全不改 core，新壳自带中文词表与胶水（代价：文案与 Android 端各写一份，长期漂移）；B 只提 i18n 与 ID 分配进 core 并升 rev（代价：Android pin 要跟着动，`SNAPSHOT_VERSION=4` 的兼容语义需重审）；C 冻结 core，把缺口写进 `docs/DIFFERENCES.md` 后续单独立项。
- 不决定的后果：P3 之后每个文案/命令都要临时决策一次。
- 建议：**C 起步，A 落地**——本轮不改 core，中文词表在壳侧建一份可核对的词表文件，并在 DIFFERENCES 里挂账。
- **决定（2026-10-14）：不改 core。**缺口按最小修改另议，先记账不先动手。

## 2. gpui 上游锚点与升级策略

- 事实（2026-10-14 修订）：发布版 `gpui 0.2.2` **能在本机装、编、起窗**（ADR-001 第六节实测记录），旧版这里写的"无法独立构建（兄弟 crate 未发布）"是错的，已撤回；它的真实代价是**停在 2025-10-22**，比上游晚约 12 个月。当前 main 拆出的 `gpui_platform`/`gpui_windows` 确实未发布，所以拿最新官方代码只能走 git。官方 README 自述 pre-1.0、经常 breaking。
- 选项：A1 `gpui =0.2.2`（零 git，已验证）/ A2 git 钉 tag `v1.23.3`（2026-10-12，最新但引入 git 依赖，解析未测）/ B Kit（`gpui-pre 0.3.9` + `gpui-fast 0.1.7` + `gpui-kit 0.7.3`，零 git，按周从上游打快照）。
- 代价：钉 tag 意味着遇到上游 IME bug 时不能立刻拿修复；跟 main 意味着每次同步都可能撞 API 断裂。
- 建议：**钉 tag，锁 Cargo.lock，升级单独走 ADR**，禁止 `branch = "main"`。

## 3. 组件栈：官方 gpui 自绘 vs gpui-kit（fork）

- 事实：gpui-kit 0.7.3 依赖 Longbridge 自己的 `gpui-fast`/`gpui-pre`，与官方 gpui 不兼容；官方侧要自己写虚拟列表、锚定弹层、表格、主题切换。
- 代价对比：官方路线的自研量集中在 P2/P4（虚拟列表 + 弹层 + 表格三件），但 IME 行为与 Zed 同源可追；gpui-kit 路线省掉这三件，代价是绑 fork，且 fork 的 Windows IME 行为是**另一个未验证的未知数**。
- 建议：先跑 `docs/ADR-001-GPUI-STACK.md` 第 6 节的 7 条探针，探针结果决定；**不要在探针前锁定**。
- **决定：两条栈都评估，不预先排斥 Kit**；判据是输入效果、维护成本、组件能力三项，写成可对比的结论而不是感觉。

## 4. 应用标识、数据目录与双版本共存

- 事实：core 的 `data_location.rs` 里 `APP_DIR_NAME = "Quire"`、`DB_NAME = "quire.db"`，`--db` 压倒一切（`decide`，166），还有 `--portable` 与 legacy `appdata` 迁移逻辑。同一库**不允许两版并发写**（`docs/07`）。
- 待定：新壳用 `Quire GPUI` 目录还是共用 `Quire`；是否支持 `--portable`；是否注册独立 AppUserModelID（影响任务栏分组与通知归属）；托盘图标是否与旧版可区分。
- 代价：共用目录会让"误开真实库"从可能变成必然；完全独立则用户每次对比要手动导库副本。
- 建议：开发期默认落在 `%LOCALAPPDATA%\QuireGPUI\`（该目录正常可写），启动时打印实际库路径（对齐用户"要能诊断"的要求）；**"绝不自动发现/迁移旧版真实库"是硬规则**，`--db` 只是指向测试副本的手段，不是"不传 --db 就不许写"。portable 与 AppUserModelID 细节放兼容阶段，不阻塞 P1。（docs/16 第 4 条指出原建议把两套规则写冲突了，此处采纳。）
- **决定：独立数据目录 + 保留旧版并存。**两版不并发写同一库。

## 5. 参考图基线是否冻结为验收基线

- 事实：本轮 312 张图采自 HEAD `47ef6f8` + 10 个未提交修改。旧版还在演进（`CHANGELOG.md`、`McpPage.slint` 等本轮就是脏的）。

## 6. 中文输入闸门失败时的退路

- 事实：gpui 的 Windows 中文 IME 有 5 个未关闭 issue（#59882/#59636/#59193/#64850/#65453），其中三个 S2；旧版 Slint 客户端当前可用。
- 待定：若 P1 复现，选 (a) 自绘文本层绕开 gpui 输入路径、(b) 换 gpui-kit 栈试、(c) 停在技术验证不进入复刻。
- 代价：(a) 是本项目最大的单块自研，可能比整个 P2 还贵；(c) 意味着本轮重写不成立。
- 建议：**先定 (c) 的判据**（例如"微软拼音连续输入 200 字出现丢字/候选框错位即判失败"），失败就停，不用外围页面掩盖。
- **决定：顺序是先定位并修复，再试替代栈。**注意"自绘文本"不等于解决输入法问题——预编辑、候选窗定位、提交/取消仍走系统 IME，自绘只是把同一堆问题从 gpui 输入路径搬到自己的代码里。判失败的判据仍建议照上面那条写死，避免修不动时靠感觉判断。

## 7. MCP 要不要补页面级工具

- 旧版基线事实：MCP 只有整理区 10 个工具，页面完全不在协议里（`reference/slint-desktop/src/app/mcp_tools.rs`），删除只做 tombstone。
- GPUI 实施状态：MCP 已扩展到 15 个工具；新增页面列表、按标题或块正文搜索、页面内容读取、Markdown 新建、标题修改及简单 Markdown 页面正文替换。正文替换会先验证导出/导入可无损往返；含复杂块、层级或自定义样式的页面会拒绝整页替换。锁定页面不可修改，页面工具没有彻底删除入口。该扩展超出逐项复刻基线，属于产品能力扩展。

## 8. 验收数值门槛是否照抄旧版基线

- 事实：旧版 README 0.1.26 的 10000 块 Working Set ≈124.1MB / Private ≈95.2MB；`docs/08` 写的是"不比同条件基线多 20%"。
- 待定：GPUI 是 GPU 渲染，内存画像不同（WGPU/DirectX 资源会另计），20% 这条是否仍按旧版总量算，还是拆成"堆内存"与"显存/资源"两条。
- 建议：拆两条门，堆内存按 20%，GPU 资源单列并允许正偏差但要有绝对上限；具体数字 P0 实测后定。
- 更正（采纳 docs/16 第 8 条）：旧版基线的 **Working Set 与 Private Bytes 都不是"堆内存"**，不能把 20% 这条直接改写成堆上限，也不该凭空设未测的显存绝对值。改成同机同场景分别记 Working Set、Private Bytes、CPU、帧时间、输入延迟、GPU 资源六项，先保证无无界增长与全量重建，门槛等实测数据出来再硬化。

## 9. 发布、回退与旧版处置

- 待定：候选版是否替换已安装旧版、是否共用开始菜单/卸载项、出问题回退到旧版时数据是否已可能被新壳写过（`docs/07` 要求旧→新→旧往返验证）。
- 建议：候选版**独立安装、绝不自动迁移**，切换动作留给用户手动执行，并在安装说明里写清"切换前必须关闭另一版并备份"。
- **决定（部分）：保留旧版。**即独立安装、不替换已装旧版。其余细节发布前再问。

## 10. 明确缺陷是复刻还是修掉（已定）

- 决定：**复刻外观与行为，但修掉明确缺陷**，例如同步页状态文字与 MCP 页段落在 560px 对话框右边界被硬切且不出省略号（`docs/14-REFERENCE-SHOTS.md` 第 5 条）。
- 执行口径：算"缺陷"的是旧版自己声明了正确意图却没做到（写了 `overflow: elide` 却硬裁、折行点落在可见区之外）。仅凭"新实现觉得更好看"不算缺陷，那属于 docs/01 禁止的重设计。
- 每处修复写进 `docs/DIFFERENCES.md`：旧行为、新行为、理由、验收证据（截图或量化数字），并保留旧版对应参考图路径，便于回退判断。
