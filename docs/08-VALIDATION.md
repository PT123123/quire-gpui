# 验收与证据要求

所有数值是复刻验收的建议门槛，开始实现时按旧版同机测量确认并记录；不是 GPUI 性能承诺。建立 `validation/`：环境说明、参考图/新图、diff、交互记录、测试输出、性能原始数据和问题列表。

## 参考采集

记录旧版完整 commit、工作树 dirty、core rev、renderer、构建 profile、OS、GPU、驱动、窗口逻辑/物理尺寸、DPI、字体和数据种子。新旧在同条件采集；图片按 theme/size/dpi/scene 命名。

旧版现有工具示例：`quire-shot --out <test-output.bmp> --scene <实际场景> --w 1280 --h 800 --theme jade`。使用现有支持 software 的构建，具体命令核对旧版 justfile。

**数据边界（2026-10-14 读源码更正）**：`quire-shot` 只在场景名包含 `backlinks` 或 `database` 时开库，且开的是 `SqliteRepository::in_memory()`（`src/bin/quire_shot.rs:369-380`），其余场景 `repo = None` 走内存 demo 会话。它**不接收 `--db`，不读写任何库文件**，因此本工具可安全重复采集；早前"场景会创建真实测试数据"的说法针对的是带 `--db` 的正常启动，不适用于此。仍要注意：无头进程会尝试绑定同步端口 5878/5879，被占用时打印 `os error 10048` 后继续渲染。

**单位坑**：`quire-shot` 用 `PhysicalSize::new(w, h)` 设定尺寸，所以 `--w 1280` 是 **1280 物理像素**，与系统缩放无关。这类离屏图不能充当 DPI 缩放验收证据；125%/150%/200% 必须在真窗口上测。

已完成的基线采集与它读出的事实（含 4 组重复哈希的含义、未覆盖清单）见 `docs/14-REFERENCE-SHOTS.md`；场景名清单见 `docs/15-SCENE-CATALOG.md`，采集脚本 `tools/capture-reference-shots.ps1` 内置了「场景名打错会静默渲染默认页」的 NO-EFFECT 检查。

旧版 software 截图与新 GPUI GPU 字体栅格不同，可用于布局和 token 参考；重要体验还需同机旧版默认 FemtoVG 真窗截图比较。不能要求两个不同 rasterizer 全图像素差为零。

## 视觉矩阵

- 1280×800、窄窗口约 900×700、1920×1080；窗口最小尺寸按旧版限制补测。
- 100%/125%/150%/200% DPI；记录尺寸单位，避免把逻辑 1280 与物理 1280 混比。
- 全部 12 theme + system 明/暗；四个渐变全页、scroll、resize、多窗口。
- 主壳、空页、长文档、全块、封面、图标、页菜单、slash、marks、搜索/命令/查找、版本历史。
- 数据库全部视图与配置弹层；笔记/任务/详情/多选/标签/撤销条；设置所有入口；同步/MCP 状态；速记。
- hover/pressed/focus/disabled、长标题、无结果、失败提示、模态与锚定弹层。

建议关键几何偏差≤2 逻辑像素、字号/token 数值一致；纯色大区域每通道偏差≤2/255（排除边缘、透明合成和截图色彩管理差异）；渐变采样与参考一致、方向/连续性无误。文本抗锯齿单独 mask，不能 mask 掉文本区域来掩盖错误字体/行高。

验收看 diff 和并排图，检查换行位置、baseline、颜色、面板边界和命中区域。全图相似度只作辅助，不作为“完美复刻”的唯一结论。记录每项例外和原因。

## 动效

主题切换、侧栏折叠、hover/pressed、菜单等逐项核对时长/easing。采集起始、中间、结束帧，证明真实插值而非终态截图；动画停止后观察刷新/CPU。保留交互期间滚动和点击可用性。

## 编辑与交互

真实 OS 中文输入测试不可由合成文本替代。按 docs/05-EDITOR 案例执行；另测鼠标选择、拖动落点、菜单边界、Escape 层级、焦点恢复、Tab 顺序、速记/主窗切换。

有意义的自动化覆盖：输入→core 命令/undo 的正确性、UTF 位置转换、composition 状态、selection geometry、可变高滚动锚点、异步旧结果丢弃、批量撤销、保存失败保留。不要只测试函数返回自己刚写进去的常量。

## 数据

测试库创建→编辑→保存→退出→重开→旧版读取，比较语义内容/ID/marks/树/属性/附件哈希。测试失败提交、崩溃重启、只读、损坏库恢复、未知设置、延迟删除超时/撤销、MCP 写后 UI 刷新。

同步使用独立测试库/设备，验证双向增删改、冲突、断连和协议拒绝。保留状态日志，但脱敏路径与设备信息。

## 性能

同机 release 构建重复测：空壳、1000 块、10000 块、连续滚动、100 页切换、10000 块里持续输入、数据库大表、整理区大列表。记录启动到首帧/可输入、Working Set、Private Bytes、CPU（说明按一核或整机）、输入到显示延迟和帧时间 p50/p95/p99。

旧版 README 的 0.1.26 示例：10000 块 Working Set 约 124.1MB/Private 95.2MB，空壳约 107.8/79.1MB；具体同机当前值优先，不把历史值直接当硬门槛。建议新实现关键场景内存不比同条件基线多 20%以上、静止无焦点 CPU 接近 0（目标低于一核 1%）；输入/滚动 p95 不退化，原因和例外单独讨论。

性能未实测就不能写“GPUI 更快、更省内存”。截图能生成也不能证明渲染帧率、输入延迟或候选框正确。

### 闲置内存现状（2026-11-06 同机实测，非承诺）

夹具：`tools/measure-runtime.ps1`，release 产物、1600×900、warmup 2s、8s@250ms 采样、隔离 `%TEMP%` SQLite、采样后强杀、全程无编辑；每场景两臂。原始 json + 探针文本落 `benchmarks/results/idle-memory-2026-11-06/`。

拿这张表和历史数字对比之前先对齐窗口面积：Private 里有一项按窗口像素线性走（实测每百万像素约 20MB），旧版 Slint + FemtoVG 的所有读数都是它自己的默认窗 1280×800，和这里的 1600×900 差 0.42 百万像素、约 8–9MB。本轮就栽过一次，细节与对齐后的比较在下面「83MB 地板的实测分解」末尾。

| 场景 | Private 末值 | Private 峰值 | 归因 |
| --- | --- | --- | --- |
| 空白页 | 83.1 / 83.4MB | 113MB | 固定地板；构成见下面「83MB 地板的实测分解」：约 54MB 与窗口无关 + 约 29MB 随窗口面积走的渲染表面 |
| 整库 30064 块载入 | +约 30MB | — | quire-core `Document.pages` 启动全量常驻（外部依赖，本层不动） |
| 10k 块页（实体封顶后） | 109.1 / 115.1MB | 133MB | 地板 + 整库 + 常驻窗口内约 121 个 `TextInput` 实体 |
| 10k 块页（改前，整页实体） | 130–160MB | 153–169MB | 10002 个 `TextInput` 实体各带 FocusHandle/订阅/Entity 表槽，1.08MB 文本被放大成约 18MB |

优化空间（剩余、按性价比，完整清单与每条的收益算法见本节末「闲置内存优化清单」）：① 固定地板约 83MB：约 54MB 与窗口面积无关、这一层拆不动，另外约 29MB 是 5 份随窗口面积走的渲染表面，能动它的是 vendor gpui 的 `PATH_MULTISAMPLE_COUNT`（4→2 约 −11.6MB、4→1 约 −17.4MB @1600×900；本文件初稿写的 −23MB 算重了，那是连 MSAA 纹理整块删掉的收益，不是改常数的收益，已更正）；② 整库常驻约 30MB 要 quire-core 改按需分页载入，属外部 crate，本轮按约束不改；③ 视口外实体已封顶到 `±120`，**这条现在按算术划掉**：上面记过 10002 个实体约 18MB，即每个约 1.8KB，`±120` 两侧的常驻量级只有 0.5MB，收紧余量的收益不到 1MB，却要重跑滚动后键入的行为门，不划算。CPU 与启动到句柄就位在本轮测量里被噪声主导（1–8% 抖动），未做归因，不写"更快"。

### 83MB 地板的实测分解（2026-11-06）

两条互相独立的量法。第一条是窗口面积扫描：同一 release 产物、同一空隔离库，只改窗口尺寸，Private 末值随面积走。

| 窗口 | 面积 | Private 末值 | 出处 |
| --- | --- | --- | --- |
| 1600×900 | 1.44 百万像素 | 83.2 / 83.5MB | 尺寸扫描两臂 |
| 1280×800 | 1.02 百万像素 | 73.1MB | 尺寸扫描 |
| 924×591（最小窗） | 0.55 百万像素 | 65.1 / 65.7MB | 尺寸扫描两臂 |
| 1600×900 对 924×591 | 差 0.89 百万像素 | 差 18.2MB（扫描）/ 18.9MB（另一次双臂的进程计数器读数） | 两者独立 |
| 1600×900（规范产物复测） | 1.44 百万像素 | 82.7 / 87.0MB | 端点复测两臂 |
| 924×591（规范产物复测） | 0.55 百万像素 | 64.1 / 63.6MB | 端点复测两臂 |
| 1280×800（规范产物复测） | 1.02 百万像素 | 73.3 / 73.4MB（Working Set 96.9 / 96.9MB） | 对齐旧版默认窗口的两臂 |

产物身份要交代清楚：上面扫描的前三行与逐页归因跑的是 18:11 那次构建出的 28,159,488B exe；`cargo build --release --locked` 之后规范产物回到 26,577,408B（sha256 `1225b9c6c554…`、FileVersion 仍 0.1.18.0），后三行是用规范产物重跑的两端加中间点。1280×800 那一对落在 73.3 与 73.4（Working Set 都是 96.9），而 1600×900 那一对落在 82.7 与 87.0——**同一台机器、同一产物、同一尺寸的跑动噪声可到 ±4MB，但也可以小到 0.1MB**，所以只认端点差与双臂同值的行，不认单臂绝对值。

还有一批要如实记下来：10:53–10:54 UTC 的第二次端点复测（`recheck2-*` 四臂）整体抬高，1600×900 读到 94.9 / 89.8，924×591 读到 71.3 / 72.2，Private 峰值也跟着从 112–113 抬到 117.4–118.3；一分钟后同一产物的 1280×800 两臂又回到 73.3 / 73.4、峰值 113.0 / 113.1。抬的是整个批次（含峰值），不是某一只窗。

抬高的原因**没归因**，但"是注入进程搞的"这个猜测本轮先被削了一刀：`benchmarks/scripts/modprobe.ps1` 在一只正常态臂上（1600×900，Private 末值 83.8、峰值 113.8）把 65 个模块全列了出来，第三方只有两颗——Flowtary 的 `filedlg_hook64_1.1.29.10.dll` 映射 0.141MB、Windhawk 的 `invisible-borders_1.0.0_501102.dll` 0.098MB，合计 0.24MB（映射量不等于驻留，但这两颗在正常臂里就在，所以它们不是"这批比那批高 10MB"的差别来源）。真要钉死，得在抬高那批正在发生的时候同批跑一次 modprobe 对账，看多出的是哪颗或哪段堆——这条排在优化清单第 1 条之后。它先把"跑动噪声 ±4MB"这句改弱成"通常 ±4MB，偶发整批 +7 到 +12MB"，但不影响结论：模型用的是端点差，而跨栈比较用的是 1280×800 那三个独立时刻的读数（10:21 的 73.1、10:55 的 73.3 与 73.4）。

面积项 = 18.2–18.9MB ÷ 0.89 百万像素 ≈ **每百万像素 20.1–21.1MB**（两点式取端点差：17.95MB ÷ 0.894MP = 20.08）。代码里的账（`vendor/gpui-0.2.2/src/platform/windows/directx_renderer.rs` 的 `PATH_MULTISAMPLE_COUNT = 4`、`create_path_intermediate_texture`、`create_path_intermediate_msaa_texture_and_view`，`BUFFER_COUNT = 3`）：`B8G8R8A8` 每像素 4 字节，中间目标 1 份 + MSAA 目标 4 份 = 5 份 × 4MB/百万像素 = **正好 20MB/百万像素**。也就是说 Private 里只装得下这 5 份，swapchain 那 3 份不在本进程 Private 上。把两条端点各自回代固定项：1600×900 得 54.4MB，最小窗也得 54.4MB——**两条独立测量在固定项上对齐到 0.1MB**；再用中间点 1280×800 验一次，模型预测 74.9MB、实测 73.1MB（本轮又加了两臂 73.3 / 73.4），差 1.8MB 以内，在噪声内。

这些是 GPU 资源，为什么会记在进程的私有内存而不是"显存"上，一句话交代清楚：本机 `Win32_VideoController` 只有 `Intel(R) Arc(TM) Graphics`（另一颗是 Oray 虚拟显示驱动），**没有独显**——核显没有本地帧缓冲，GPU 资源本来就住在同一根内存条上，WDDM 下驱动替进程做的分配挂在进程上下文里，`PrivateMemorySize64` 就把它算进来了。有独显时驱动是否另存一份本地副本，本机测不了，不写成结论。Task Manager 那个 GPU 列本轮也取不到：`\GPU Process Memory` 计数器在这台机器上没有按 PID 的实例，所以口径只能是进程私有字节。

反过来说，Private 也不是"所有 GPU 分配"的大杂烩，有一条实测能证：代码里按窗口尺寸做的分配实际有 8 份（交换链 `BUFFER_COUNT = 3` + 中间目标 1 份 + MSAA 那 1 张 4 采样 = 4 份像素量），可斜率只对应 5 份——**交换链那 3 份没落在本进程私有内存上**（合理推断是 flip-model 下按句柄交给 DWM、没映射进我们的地址空间；这是推断，不是实测）。还有一处常见的直觉要按住：页面内容本身几乎不走 GPU，字形图集默认只有 1024×1024（单通道 1 字节/像素 = 1MB、彩色 4 字节 = 4MB，`vendor/gpui-0.2.2/src/platform/windows/directx_atlas.rs:153`、`:171`、`:176`），所以 10k 块页相对空白壳那 +26～32MB 在 CPU 堆上——也正因为它在 CPU 堆上，才归这一层管、才量化得动、才有下面清单里第 3、5 条可讨论。

模型：`闲置 Private ≈ 54.4MB + 20.1MB × 窗口百万像素`（1600×900 → 83.3，实测 83.2–83.5；最小窗 → 65.4，实测 65.1–65.7）。规范产物两臂各自回代得 52.9 / 52.8MB（那两臂端点差 18.6MB，斜率略低），离群一臂 57.2MB——线性关系站得住，绝对值受 ±4MB 噪声限制，固定项取 53–55MB 这一带。下面那批整体抬高的复测把这一带放宽到 53–61MB（自洽截距 56.9 / 61.4），不影响任何结论，因为截距只会让"到不了 20MB"更硬。

第二条量法本想做逐页归因（QueryWorkingSet + VirtualQueryEx 按 IMAGE / MAPPED / PRIVATE 分桶），但它没能通过自证，**下面的表只当方向性线索，不当归属**：

| 桶 | 1600×900 | 924×591 | 状态 |
| --- | --- | --- | --- |
| 最大单桶（`AllocationBase=0`） | 53.9MB | 44.3MB | 可疑：该区间的地址经 `VirtualQueryEx` 落到未校验区，也可能是条目步长解错的产物（`PSAPI_WORKING_SET_BLOCK` 我按 16 字节解出可用模块名、按 8 字节解出全垃圾，两种都没拿到官方布局确认） |
| 次大桶（共享计数 28，提交 25.2 / 12.6MB） | 12.6MB | 6.3MB | 提交量对上"5 份表面 ≈ 28.8 / 10.9MB" |
| IMAGE 合计 | 21.4MB | 21.3MB | 与窗口尺寸无关，含 Intel 图形栈 igd10umt64xe 3.1 + igc64 2.5 + igdgmm 0.7 ≈ 6.3MB |
| MAPPED 合计 | 1.4MB | 1.4MB | 与窗口尺寸无关 |
| Private 峰值 | 114.0MB | 113.5MB | **与窗口尺寸无关**（规范产物复测四臂 112.6 / 112.6 / 113.0 / 112.1，同样不随尺寸动） |

"分桶之和 ≈ WS"这条不构成验证：垃圾页也会全落进同一个桶，闭合是恒等的。所以固定项的**大小**只认扫描法那条独立结论（约 54MB），逐页表里恰好也是 53.9MB 这件事记为待查，不记为证明。

另有一条不依赖上面任何推断的旁证：模块表（`Process.Modules` 的镜像量，本机 Intel 核显）里 `igc64.dll` 单颗映射 82.3MB、`igd10umt64xe.DLL` 24.9MB、`igdgmm64.dll` 5.2MB、`igd10iumd64.dll` 5.1MB、`d3d11.dll` 2.4MB——图形驱动用户态在 Windows 上是直接映进本进程的，映射量不等于驻留，但这解释了为什么"空白壳"的地板里有一块怎么都不肯降。

三件事能定死，写成分数而不是感觉：

1. 面积那一半（1600×900 下约 29MB = 5 份窗口尺寸的表面）里，真正能动的是 vendored gpui 的一个常数。一份窗口尺寸表面 = 4.02MB/百万像素（斜率 20.1 ÷ 5 份），代码在 `directx_renderer.rs:1097-1098` 无条件同时建中间目标（`SampleDesc.Count = 1`）和 MSAA 目标（`Count = PATH_MULTISAMPLE_COUNT`，`directx_renderer.rs:32` 现为 4），所以：4→2 少 2 份 = −11.6MB @1600×900（−8.2MB @1280×800）；4→1 少 3 份 = −17.4MB @1600×900（−12.3MB @1280×800）。**本文件初稿写的 −23MB 是算重了**——那是 5 份只剩 1 份、也就是把 MSAA 纹理的分配整块删掉（还要顺带改 resolve 路径）才有的收益，不是改这个常数能拿到的，已更正。另有一条实现风险要写明：MSAA  desc 的 `Quality` 用的是 `D3D11_STANDARD_MULTISAMPLE_PATTERN`，`Count` 降到 1 时这个组合是否被 `CreateTexture2D` 接受没验过，消融实验第一步得先确认程序还能起来。代价是路径光栅那趟硬件 MSAA 变浅，圆角与矢量边缘会有锯齿；这是改 vendor 依赖，要 ADR、要真人看画质，本轮没做消融实验（Windows 侧没有对应的运行时开关，只有 metal 有 `ZED_PATH_SAMPLE_COUNT`）。`BUFFER_COUNT`（`directx_renderer.rs:1389`）3→2 对本层报出的 Private 预期 ≈ 0，因为交换链那 3 份压根不在本进程 Private 上。
2. `GPUI_DISABLE_DIRECT_COMPOSITION=1`（现成开关，不用改源码）实测 −2.5MB，落在同机 ±3–4MB 的跑动噪声内（同一天 "on" 三臂读到 87.1 / 86.9 / 83.2–83.5），不是杠杆。
3. 剩下约 54MB 的固定项才是大头。这一条只靠扫描法和 Windows 的定义站住：Private 计数按定义不含文件映射的镜像视图，所以它不是"DLL 驻留"那一块；再往下拆到具体归属（DWrite/ICU 字形缓存、asset pack、SQLite 页缓存、gpui 元素与文本缓存、驱动私有池各占多少）**本轮没有实测数**，逐页那条路没走通，别当结论用。

**"100→20" 这个量级到不了。** 20MB 比约 54MB 的固定项本身还小，也就是在砍掉任何一块渲染表面之前就已经不够；把 MSAA 纹理的分配整块删掉（不是只改常数，见上面第 1 条）后，这套栈在 1600×900 的算术下界约 60MB（54.4 + 1 份中间目标 5.8）。交换链减缓冲对 Private 没有贡献，那条不是出口。

**先撤回一条本文件上一版写错的结论。** 上一版说"两套毫无关系的渲染栈落在同一个约 80MB 上，所以这块地板是品类成本"。那条比较的腿是错的：GPUI 用的是 1600×900 的 83.2/83.5MB，旧版（Slint + FemtoVG）用的是空白壳 79.1MB——而旧版那个读数根本不在 1600×900 上量。`quire-desktop/ui/AppWindow.slint:527-528` 写死 `preferred-width: 1280px; preferred-height: 800px;`，`benchmarks/scripts/bench_matrix.ps1` 全文没有 `MoveWindow`/`SetWindowPos`，不改尺寸，所以旧版 README 那张表整列都是 1280×800。两臂面积差 0.42 百万像素，按本文件实测的斜率就是 8–9MB。拿不同面积的两臂比出"相等"，是我自己造出来的，撤回。

旧版那侧还有一条要排除的可能：`quire-desktop/src/main.rs:854` 会在启动时读回上一会话的窗口矩形并 `set_size`，所以它的名义尺寸本来可能被存档改写。排除掉了——`benchmarks/scripts/bench_matrix.ps1:65` 的 `Clear-Database` 在每场之前删掉 `.db`/`-wal`/`-shm`/五个 `.bak`，夹具库是全新的、里面没有几何记录，于是量到的就是 Slint 的 `preferred` 1280×800。

对齐面积后本轮重测了两臂（规范产物、1280×800、同一空隔离库夹具）：

| 栈 | 窗口 | Private 末值 | Working Set 末值 | 出处 |
| --- | --- | --- | --- | --- |
| GPUI 0.1.18 | 1280×800 | 73.3 / 73.4MB | 96.9 / 96.9MB | 本轮 `canon-1280x800-a/b` |
| Slint + FemtoVG 0.1.26 | 1280×800 | 79.1MB | 107.8MB | `quire-desktop/README.md:26`（机型三项已对本机核对相等，同机可比） |

**所以"Slint + FemtoVG 闲置比 GPUI 低很多"不成立，方向是反的**：同面积下 GPUI 低 5.7–5.8MB Private、低 10.9MB Working Set。Private 那 5.7MB 落在同机 ±4MB 噪声带的边上，算不上强结论；Working Set 的 10.9MB 更实。

这条比较的两侧腿不一样硬，要说明白：GPUI 这侧是本轮同夹具重测的三个独立时刻（73.1 / 73.3 / 73.4，两臂到 0.1MB），旧版那侧只有 2026-10-17 那一次矩阵的单臂记录——本机现在已经没有旧版可执行文件（`%LOCALAPPDATA%` 与 `%APPDATA%` 下都搜不到 `quire-slint*.exe`，`quire-desktop/target/release/` 也没有），要用同一把尺子复量旧版得先把它编出来。所以下面的结论只到"旧版没有更低"这一级，不到"GPUI 精确低 5.7MB"。

面积项的机制两套栈确实不同，但它解释不了绝对高低：gpui 在 Windows 上无条件常驻 5 份窗口尺寸表面（1 份中间目标 + 4 份 MSAA，`PATH_MULTISAMPLE_COUNT = 4`），FemtoVG 走 GL 路径光栅，它的常驻目标不按这个常数复制份数。1280×800 下这一项只有约 20MB，比约 54MB 的公共固定项小，所以壳对壳的差被固定项主导——"约 54MB 那一块与渲染栈无关"这句仍然站得住（它是扫描法在 GPUI 上量出的截距，旧版同机同数量级的空白壳是旁证），但"两套栈落在同一个数"那句作废。

真正能看出差异的地方在内容那一侧，不在壳：旧版 10 000 块相对空白壳是 +16.1MB Private（79.1→95.2，`quire-desktop/README.md:28`）；GPUI 的 10k 块页相对同尺寸空白壳是 +26.0 / +31.7MB（1600×900 的 83.1/83.4→109.1/115.1，见上面「闲置内存现状」表）。**这两组不是同一夹具**——块正文长度与场景定义都不同，只能算同量级参照，不能当严格对照。方向上 GPUI 是"壳更便宜、大块页更贵"，要继续压内存，性价比在页内常驻实体那一条，不在渲染栈那一条。

真要做到 20MB 得换一类栈（GDI/Direct2D 手绘、不留常驻场景目标、不走合成），那是重写；而且本机是 Intel 核显，驱动用户态直接映进进程，20MB 在 Windows 上基本不成立。

一个必须单独点出来的风险：面积那一项按窗口像素线性走。3840×2160 是 8.3 百万像素，按上面的模型推算 Private 会到约 220MB（**外推，未实测**），MSAA 目标在那种尺寸下比其余一切都大。真要压地板，先在高分屏上量一臂再决定动不动 `PATH_MULTISAMPLE_COUNT`。

原始读数：`benchmarks/results/idle-memory-2026-11-06/floor/`（尺寸扫描五臂 json、两档逐页归因 walk 文本、direct composition 三臂、规范产物端点复测两批共八臂 json（`recheck-*` 为正常批次，`recheck2-*` 为整体抬高那批）、规范产物 1280×800 对齐两臂 json、正常态臂的模块清单 `modprobe-now-modules.tsv`，外加六个量法脚本；模块探针本身在 `benchmarks/scripts/modprobe.ps1`）。
