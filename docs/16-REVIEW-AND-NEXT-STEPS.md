## 当前阶段

参考源码、参数索引、场景图与入口矩阵补深是有价值的工作。但 DELIVERY-STATUS 明确未建 Rust 工程、未运行 GPUI，因此这是 P0 前期准备进展，不能称应用实现一大半。本轮复核阅读文档和抽查一手资料，没有重新验证全部截图或全部 API。

原始交接包缺少现采图片、完整语义矩阵及 GPUI 编译探针，这是第一轮真实缺口。截图场景的数据边界更正合理；原文应明确限定为截图工具内部生成的内存数据，不能暗示截图工具会写用户数据库。

## 必须先修正的选型证据

### 1. 不能用当前仓库结构证明发布版无法安装

ADR-001 第一节将“当前 main 的同版本包已拆分出未发布 crate”作为“crates.io gpui 0.2.2 装不起来”的证据，混淆了两个源码版本。

本轮检查 [已发布 gpui 0.2.2 的标准化 Cargo.toml](https://docs.rs/crate/gpui/0.2.2/source/Cargo.toml)：没有 gpui_platform 依赖；collections、sum_tree 等使用 gpui_collections、gpui_sum_tree 这样的发布包别名。当前仓库存在另一些未发布 crate，不能反证该旧发布包本身缺依赖。

正确结论：当前 Git 源码和旧发布版的依赖/API 不同，示例不能混用；**发布版在本机 Windows 能否构建尚未验证**。原来的“只能 Git”“cargo add 是死路”应撤回或改为待测，不得继续当作硬事实。这里也不宣称发布版已经可用：仍可能存在编译/工具链/功能问题，需要最小工程日志证明。

### 2. 组件栈不兼容与“另一套框架”应分开

[GPUI Kit 官方文档](https://gpui-kit.com/docs/)称 gpui-pre 是版本固定的 GPUI 快照。具体包来源、fork patch、类型身份和版本约束需检查所选 release 的 Cargo.toml/lock。不能因别名不同便判定完全不同框架，也不能默认不同快照可混装。

工程原则仍成立：选定一套兼容依赖图，使用组件栈提供的同一 GPUI 类型；禁止混装不兼容快照。选官方还是 Kit，应由输入验证、可维护性、组件复用和复刻成本共同决定，不能规定只有官方失败才允许评估 Kit。

### 3. 不扩大工具链与自研结论

Zed 完整仓库的 wasmtime、Spectre、Rust toolchain 要求不能未经依赖追踪全部套到独立 GPUI 程序。先编译目标最小应用，缺哪个组件再补哪个，并记录错误。不要仅因 VS 某目录不存在就把它设为所有路线的硬阻塞。

官方路线也不要先写“虚拟列表等全部自研”；先核对锁定版本的 list、uniform_list、自定义 element 和输入接口，再确定缺失部分。

## 九条事项的建议处理

以下均为建议，供用户/实现 AI 明确采纳；不把建议记成用户批准。

1. **core：第一阶段冻结 db0e95f。** 中文文案放壳侧，设备身份和平台协调按原边界复用，完全可以启动验证。之后确有通用能力缺口，再提出向后兼容的最小 core 补丁。移动文案或内部 ID 分配不天然要求改 snapshot version；是否影响协议、schema、Android pin需分别分析，不能捆绑推断。
2. **依赖：锁可运行的完整 commit/版本及 lock。** tag 可以作候选锚点，但记录它解析到的 SHA。遇到必需修复可以有依据地升级或维护小补丁，不要求每次正常依赖调整都重新询问用户。
3. **组件：允许最小原型比较官方与 Kit。** 两条路线使用隔离工程和依赖图；不要先迁移全部界面。能够保留 Quire 外观并减少可靠性风险者优先。
4. **共存：独立 QuireGPUI 标识和开发数据目录。** 默认独立测试/开发库，显式 --db 指向测试副本。没有必要同时规定“强制 --db 才可写”和“默认目录正常可写”这两套冲突规则；建议默认独立目录可写，但绝不自动发现/迁移旧版真实库。portable 放后续兼容阶段，不阻塞 P1。
5. **基线：冻结 baseline-2026-10-14。** 新旧缺陷差异明确记录，旧版后续变更按需单独纳入。不要边实现边无条件重采、追逐移动基线。
6. **IME：阻塞严重问题，分级处理一般差异。** 丢字/重复提交/改错范围/无法选词/输入崩溃为严重失败；候选框持续脱离 caret、挡住操作也需修复。单条上游 issue 存在或一次轻微视觉差异不自动否决整个路线。先排除应用输入适配错误，再考虑上游修复/小补丁、替代兼容栈；仍不可靠则停在验证阶段并向用户报告。自绘文本不会自动绕开 GPUI 的 TSF/IME 路径，不应直接承诺靠自绘解决。
7. **MCP：复刻现有协议和权限。** 页面级工具扩展不属本轮范围，不需要为此暂停原功能迁移。
8. **性能：同机同场景测量，建议门槛暂不硬化。** Working Set、Private Bytes、CPU、帧时间、输入延迟、GPU 内存分别记录；Working Set/Private 都不等于“堆内存”。不能把原 20% 目标直接改成堆上限，也不能随意设未测的显存绝对值。先防无界增长/全量重建，再根据数据确定优化目标。
9. **发布：候选版独立安装、保留旧版。** 沿用原任务边界，替换安装和真实库切换留到候选验收后另行决定，不阻塞开发。

## 完美复刻与缺陷处理

复刻布局、设计、功能和熟悉的操作；不复制明确的文字裁切、丢焦点或保存缺陷。同步/MCP 的半字裁切应在新 UI 修复，优先用正确布局约束、换行、最小尺寸/滚动解决，而不是全局放大/重设计对话框。记录为有意差异，并展示同条件旧图/新图。

## 下一轮的具体交付

停止以补更多文档和截图作为主要成果，转向可运行证据：

1. 修正 ADR-001 的发布版/当前仓库混淆；确认候选依赖，不要求先研究完整生态。
2. 建独立最小 Rust 工程、锁依赖、实际运行 Windows 窗口。保存准确命令、工具链和成功/失败日志。
3. 同一探针窗口放文本输入和根渐变。测微软拼音输入/选词/替换选区/撤销、长中文与 emoji，以及窗口缩放后的候选框。明确机器可测部分与需人工输入部分。
4. 输入成立后接固定 core，打通一个页面的加载、编辑、拆合、undo、保存重启；逐步验证 styled layout 和可变高万块列表。
5. 为已实现范围补行为语义和验收条目。自动抽取清单保持生成产物；人工语义/进度另存稳定 ID 的 sidecar 文件并让生成器合并，避免重跑覆盖人工结论。callback 行数不是用户功能数量。

原七项探针应分阶段执行：最小窗口/基础输入先跑；富文本、万块、完整托盘属于后续可运行验证，不要把全部实现都放在“开始 P1 之前”的前置门槛里形成循环。

本建议不授权写旧版用户库、改 core、安装系统组件或替换已安装应用。是否采纳建议请在决策记录中准确标注来源；不要伪造“用户已拍板”。
